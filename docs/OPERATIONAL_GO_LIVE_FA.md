# راهنمای آماده‌سازی بهره‌برداری E.Y.T ERP

> هدف این سند: رساندن مخزن به یک راه‌اندازی قابل‌تکرار و قابل‌ممیزی. وجود کد و سبز بودن CI به‌تنهایی به معنی استقرار موفق در سرور واقعی نیست.

## وضعیت قطعی و مرز ادعاها

- اجرای محلی/آزمایشی از مسیر Docker Compose در CI تعریف شده است.
- سرویس‌های اصلی Compose شامل PostgreSQL، migration، API، finance-worker، کاتالوگ و n8n اختیاری هستند.
- مسیر کنترل‌شده تولید و QC در مستندات API تعریف شده است.
- ایجنت مالی روزانه باید فقط‌خواندنی بماند؛ پیشنهادهایش تا زمان تأیید مجاز به تغییر سفارش، قیمت، پرداخت یا سند مالی نیستند.
- **استقرار روی سرور واقعی، اتصال دامنه و TLS، صحت backup/restore و صحت داده‌های عملیاتی در این سند تأیید نشده‌اند.** فقط پس از اجرای چک‌لیست پایین می‌توان وضعیت را «آماده بهره‌برداری» اعلام کرد.

## ترتیب راه‌اندازی

### 1. پیش‌نیازهای محیط

- Docker Engine و Docker Compose نصب و به‌روز باشند.
- یک سرور اختصاصی/قابل‌اعتماد با فضای کافی برای دیتابیس، لاگ‌ها و نسخه‌های پشتیبان آماده باشد.
- DNS و TLS برای دامنه‌های مورد استفاده تنظیم شوند؛ پورت دیتابیس به اینترنت عمومی باز نشود.
- ساعت سرور همگام باشد و منطقه زمانی فرایندهای زمان‌بندی‌شده روی `Asia/Tehran` تنظیم شود.
- دسترسی shell و دسترسی مشاهده لاگ‌ها برای مسئول استقرار ثبت شده باشد.

### 2. اسرار و تنظیمات

فایل `.env.example` فقط الگو است. مقادیر نمونه را در محیط واقعی استفاده نکنید.

حداقل مقادیر لازم برای Compose فعلی:
- `POSTGRES_PASSWORD`
- `DATABASE_URL` با hostname داخلی سرویس دیتابیس در Compose، معمولاً `db`
- `JWT_SECRET` و `BOOTSTRAP_SECRET` مستقل و تصادفی
- `RUBIKA_WORKSHOP_WEBHOOK_SECRET`
- برای فعال‌سازی پروفایل automation: `N8N_ENCRYPTION_KEY` و `EYT_ERP_CHANNEL_TOKEN`

نکات امنیتی:
- اسرار را در Git، گزارش خطا، تصویر صفحه یا پیام‌رسان ثبت نکنید.
- `BOOTSTRAP_SECRET` را پس از راه‌اندازی اولیه طبق فرایند امن محیط تعویض/غیرفعال کنید؛ endpoint bootstrap را عمومی رها نکنید.
- برای `CORS_ORIGINS` فقط originهای واقعی و لازم را تعیین کنید.
- `CHANNEL_INTAKE_SECRET`، توکن کانال داخلی و رمز webhook روبیکا باید جداگانه تولید و نگهداری شوند.
- n8n را بدون TLS و احراز هویت مناسب به اینترنت عمومی منتشر نکنید.
- برای تولید، از `latest` به‌عنوان tag پایدار سرویس n8n استفاده نکنید؛ نسخه مشخص و آزموده‌شده را pin کنید.

### 3. پیش از هر استقرار

از ریشه مخزن اجرا کنید:

```bash
python scripts/verify_migration_chain.py
python scripts/verify_alembic_chain.py
python scripts/verify_migration_compatibility.py
docker compose -f docker-compose.production.yml config
```

سپس در محیط CI/محیط staging:
- همه تست‌های `pytest -q` پاس شوند.
- Compose از ابتدا build و اجرا شود.
- `/health` و `/ready` پاسخ سالم بدهند.
- کاتالوگ روی پورت 8080 پاسخ دهد و proxy API سالم باشد.
- `scripts/operational_smoke_test.py` با `BASE_URL` محیط آزمون پاس شود.
- لاگ migration، API، دیتابیس و worker از نظر خطا بررسی شود.

### 4. پشتیبان‌گیری و بازیابی

قبل از اولین داده واقعی:
1. سیاست backup زمان‌بندی‌شده و نگهداری نسخه‌ها را تعیین کنید.
2. backup را خارج از همان دیسک/سرور نگهداری کنید.
3. بازیابی backup را روی محیط جداگانه واقعاً آزمایش کنید.
4. زمان آخرین backup موفق و نتیجه آخرین restore test را ثبت کنید.
5. برای ارتقای schema، backup معتبر و روش rollback/restore داشته باشید.

تا وقتی restore آزمایش نشده، backup صرفاً فایلی است که امیدواریم روزی مفید باشد.

### 5. آزمون پذیرش جریان واقعی E.Y.T

در staging و با داده ساختگی، از ابتدا تا انتها تست کنید:

1. ساخت/تطبیق کالا با کد یکتای Product Master.
2. ثبت سفارش مشتری و کنترل دسترسی کانال.
3. بررسی موجودی و رزرو، بدون منفی شدن موجودی.
4. ایجاد سفارش تولید و BOM نسخه‌دار.
5. ثبت عملیات با مسئول/پیمانکار، ورودی، خروجی سالم، مردودی، ضایعات و هزینه.
6. ثبت QC؛ کالای مردود یا فاقد تأیید نهایی نباید به موجودی کالای نهایی آزاد شود.
7. رسید انبار کالای تأییدشده.
8. ثبت ارسال، فاکتور/مطالبه و دریافت وجه در گردش کاری مجاز.
9. اجرای دوباره درخواست‌های تکراری برای اثبات idempotency.
10. تأیید audit log و تطبیق گزارش‌ها با رکوردهای منبع.

از داده واقعی مشتری یا اطلاعات مالی واقعی در تست CI استفاده نکنید.

## قرارداد عملیاتی ایجنت‌ها

### ایجنت کارگاه / روبیکا

- پیام ورودی را به پیش‌نویس ساخت‌یافته تبدیل کند: نوع رویداد، محصول/کد، تعداد، واحد، کارگاه/پیمانکار، زمان، منبع پیام و confidence.
- تطبیق محصول فقط بر اساس Product Master معتبر انجام شود؛ مورد مبهم به صف بررسی انسانی برود.
- پیام تکراری نباید دوباره سفارش تولید/رسید/هزینه ایجاد کند.
- فقط نوع رویدادی که مجوز و مسیر ثبت مشخص دارد، با نقش مجاز ثبت شود.
- پیام‌های مالی، پرداخت، تغییر قیمت و تغییر سفارش بدون workflow تأیید معتبر فقط پیش‌نویس باقی بمانند.
- ثبت‌کننده، زمان، منبع، داده خام و شناسه idempotency برای audit حفظ شوند.

### ایجنت مالی روزانه

گزارش باید حداقل این بخش‌ها را با تاریخ مبنا و بازه مشخص نشان دهد:
- حرکت ثبت‌شده نقدی، نه ادعای مانده بانکی تأییدشده.
- مطالبات و سن مطالبات، در حد داده‌های موجود.
- سود/حاشیه سفارش از منبع واقعی هزینه و با نمایش موارد ناقص.
- سفارش‌های فاقد هزینه کامل، هشدارهای تسویه باز و اقدام پیشنهادی.
- برای هر عدد، منبع داده، زمان به‌روزرسانی و وضعیت کفایت داده.

محدودیت‌هایی که باید آشکار بمانند:
- حرکت نقدی ثبت‌شده لزوماً معادل مانده نقد قابل‌مصرف یا مانده تأییدشده بانک نیست.
- اگر ارز منابع یکسان یا قابل‌تبدیل معتبر نباشد، جمع‌زدن اثر نقدی ممنوع است؛ مقدار باید نامشخص گزارش شود.
- پیش‌بینی نقدینگی و سرمایه در گردش تا زمان اتصال منابع معتبر با وضعیت `INSUFFICIENT_DATA` بمانند.
- سود سفارش تا زمان اعتبارسنجی وضعیت سفارش و کامل بودن هزینه‌های منبع، تخمینی/مشروط تلقی شود.
- پیشنهادها `PROPOSED` هستند؛ عامل مالی حق ایجاد پرداخت، تغییر قیمت، سفارش یا سند مالی را ندارد.

## معیار نهایی Go / No-Go

راه‌اندازی فقط وقتی **GO** است که همه موارد زیر مستند و امضا شده باشند:
- [ ] CI و تست‌های integration روی commit مشخص سبز باشند.
- [ ] نسخه دقیق commit مستقرشده ثبت شده باشد.
- [ ] migration روی نسخه پشتیبان‌گرفته‌شده بدون خطا اجرا شده باشد.
- [ ] health، readiness، کاتالوگ و API از بیرون محیط به شکل امن قابل دسترس باشند.
- [ ] TLS، DNS، firewall، اسرار و دسترسی‌های RBAC بررسی شده باشند.
- [ ] backup و restore واقعی آزمایش شده باشند.
- [ ] آزمون انتهابه‌انتها با داده ساختگی پاس شده باشد.
- [ ] حداقل یک حساب مدیر و حساب‌های نقش‌محدود با دسترسی حداقلی آزمایش شده باشند.
- [ ] مانیتورینگ خطا، فضای دیسک، دیتابیس و worker و مسئول پاسخ‌گویی مشخص باشند.
- [ ] محدودیت‌های گزارش مالی و هر داده ناقص به کاربر گزارش نمایش داده شوند.

هر مورد بازِ امنیتی، migration، دسترسی غیرمجاز، اختلاف موجودی، ثبت تکراری یا شکست QC، نتیجه را **NO-GO** می‌کند.
